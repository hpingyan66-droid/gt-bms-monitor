# GT BMS Android 0.2.1-recovery.1

元の署名鍵を回収できない状況で、旧アプリとデータを残して復旧を進めるための版です。
**旧版と同じ署名ではありません。旧版への上書きAPKではありません。**

| 項目 | 旧版 | 復旧版 |
|---|---|---|
| パッケージ | `jp.k4159191.gtbms.prototype` | `jp.k4159191.gtbms.recovery` |
| ランチャー名 | GT BMS 試作版 | GT BMS 復旧版 |
| 対応する移行元 | 配布済み0.1.1 / 0.2.0の検証済みAPK | 空の新規インストールのみ |
| 署名 | 元の鍵は未回収 | 別の鍵。公開証明書情報はsigning-certificate.json |

復旧版は0.2.1のアプリ本体を別パッケージでビルドします。端末固定を前提とし、
BMSの生電流の符号を保持する既存の0.2.1修正を含みます。元のアプリ本体と
旧署名を確認するビルドスクリプトは変更していません。

## 実機への移行

1. 走行・監視を止めて安全に駐車します。可能であれば旧版からBMS CSVと走行CSVも保存します。
2. 復旧キットZIPをWindows PCの書き込み可能な場所へ全展開します。ZIP内から直接起動しないでください。
3. Python 3.9以降を用意します。未導入なら公式 https://www.python.org/downloads/windows/ を利用します。
4. 公式 https://developer.android.com/tools/releases/platform-tools からWindows版を取得し、
   `platform-tools` フォルダーを `migrate.py` の隣へ置きます。既存のPATH上のadbも利用できます。
   キットは第三者SDKバイナリを再配布しません。検証に使用したadbは37.0.1です。
5. Androidの開発者向けオプションでUSBデバッグを有効にし、USBケーブルでPCに接続します。
   画面のロックを解除して「このパソコンからのUSBデバッグ」を許可します。接続端末は1台にします。
6. **復旧版を先に開かず** `START-RECOVERY.cmd` を実行します。APKのインストールもツールが行います。
   旧アプリを一時停止してDB・WAL・設定・補助ファイル・元APKをPCへ保全し、
   ローカルのコピー上でSQLite整合性を検査してから空の復旧版へコピーします。
7. `PASS` と表示されたら「GT BMS 復旧版」を開き、記録・走行履歴・車両条件を確認します。
   Bluetooth接続から「付近のデバイス」「正確な位置情報」を、必要に応じて通知を許可します。
   OSの許可・Bluetooth接続状態は別アプリへコピーされません。
8. BMS接続は停車中に確認します。旧版と復旧版を同時に接続させないでください。
   移行後はUSBデバッグをOFFにできます。

`phone-backup-日時` 内の `original-data.tar` は移行前の生データです。
`migration-receipt.json` に件数・内容のハッシュ・旧データ不変の照合結果が残ります。
バックアップには私有の設定・走行記録が含まれます。公開GitHubへ上げないでください。

Linux/macOSでは `python3 migrate.py --adb /path/to/adb` を使用できます。
複数端末を接続する必要がある場合は `--serial` で明示します。

## 停止した場合

- `already has data`：復旧版に既存データがあります。上書きを拒否した状態です。
  初期化やアンインストールをせず、両方のアプリとバックアップを保全してください。
- `not a verified`：対象APKが検証済み0.1.1/0.2.0と一致しません。移行元を別途確認します。
- `run-as` / 権限エラー：端末側制限やデバッグ許可を確認します。root化や制限回避は不要です。
- `STOP` / USB切断：途中まで作った復旧版を自動削除しません。旧版・新規バックアップを残し、
  表示内容を共有してください。バックアップができたかどうかは実際のファイルを確認します。
- 新しい記録を始める前なら旧版を開いて元の監視を再開できます。移行後の復旧版の追加記録は
  旧版へ自動同期されません。旧版も削除せず残してください。

## データと検証の範囲

- アプリ専用の2つのSQLite DB（schema 1）、学習モデル、SharedPreferences、filesを対象にします。
- WALを含む停止中のスナップショットをPCへ取り、SQLite backup APIで確定した内容をコピーします。
- SQLite整合性・テーブル構成・各テーブルの件数と内容を確認し、端末への書き戻し後に全ファイルを
  再取得してハッシュを照合します。さらに旧アプリ側の全対象ファイルが変わっていないことを確認します。
- 元のアプリへ書き込むコマンド、アンインストール、データ消去はありません。
- 公開ソースや配布キットに個人の実測DB・CSV・署名秘密鍵は含めません。
- 実機のBMS通信、USBドライバー、OS固有制約、走行時の測位精度はクラウド上の試験で保証できません。

## 署名の保管と今後の更新

復旧版の署名秘密鍵は公開リポジトリに置かず、所有者限定の保管先で別途引き渡します。
鍵とパスワードのバックアップを別媒体にも保管してください。今後の復旧版の更新には同じ鍵と
同じパッケージを使い、versionCodeを増やします。元の鍵が見つかった場合は旧版との証明書一致を
確認してから更新経路を判断します。元の鍵の再生成を行ったとは説明しません。

ビルド時は `build_recovery.py --android-jar ... --build-tools ... --output ...
--keystore ... --password-file ...` を指定します。鍵がなければ停止し、自動生成しません。
公開の `signing-certificate.json` と証明書が違う鍵でも停止します。

CIでは `python3 -m unittest discover -s android/recovery/tests -v` と既存の2612ホストアサーション、
SDK35でのコンパイルを行います。`--unsigned` はCIのコンパイル確認用であり配布APKではありません。
`--tests` は合成データ専用のAndroid instrumentation APKも生成します。

GitHubのAndroid統合試験では、公開リリース用の署名鍵を使用せず、使い捨ての試験鍵で
未署名のテスト用APKに署名します。公開の証明書固定値は変更せず、この試験APKを配布しません。
移行元の0.2.0 APKはハッシュを固定した回帰試験用ファイルとして保全しています。
