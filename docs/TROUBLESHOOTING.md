# トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| python/pyが見つからない | Setup.ps1 -PythonExeで実体を指定。起動は.venv\Scripts\python.exeを使用 |
| 監視値が模擬のまま | config.local.jsonのmodeをbleへ変更してプログラム再起動。ヘッダーで種別を確認 |
| ValueErrorで接続できない | ローカルble_addressが空、または設定の範囲外。公開ソースへアドレスを記載しない |
| 機器を発見できない | Bluetoothオン、電池/通信圏、公式スマホアプリ切断。scanは監視停止時に実行 |
| characteristic absent | UUIDとGATTプロパティ、BMSのプロトコルを確認。名前だけでJBDと断定しない |
| 接続できるが通知0件でタイムアウト | 公式アプリを切断し、距離とRSSIを確認。2026-10-11にはこの症状から、追加のアプリ認証を使わない通常読み取りで取得・保存に成功した。根因は未確定。[段階別診断とGATT点検](AUTH_TIMEOUT_INVESTIGATION.md)を参照し、同じ認証試行を繰り返さない。通常監視を停止してから診断する |
| pair:trueにしてもPIN画面が出ない | Bleak 3.0.2のWinRT実装はCONFIRM_ONLY。OSペアリングとアプリ接続認証は別物で、設定だけでPIN入力を保証しない。認証方式を確認してから対応 |
| aiobmsbleが見つからない | `.venv\Scripts\python.exe -m pip install -r requirements-aiobmsble.txt` で任意の診断依存を導入。通常監視の必須依存ではない |
| 追加コネクターの認証に失敗する | 無応答は誤パスワードの証明ではない。auth_subscribe/auth_write/auth_wait_reply、operationの完了有無、切断を比較する。現在の対象は追加アプリ認証を使わない通常監視で取得可能。値をログ・チャットへ貼らず、推測や連続再試行をしない。追加コネクターの認証と通常JBD取得の互換性は別に判断 |
| probe成功後も履歴が増えない | probeは端末への診断表示のみ。DB保存は継続監視が担当。追加コネクターは診断専用のため、その認証結果は通常監視へ自動反映されない |
| STA/WinRTエラー | CLIから起動。pywin32等のCOM初期化を混ぜない。Bleak公式troubleshootingを確認 |
| 取得周期が2秒より長い | BLE要求の応答時間を含むため厳密な周期は保証しない。実測間隔で積算。BMS負荷を見て5〜10秒へ |
| 周期変更が409 | 走行セッションを終了してから変更。開始時と終了時の積算条件を一致させるための制約 |
| 電力・Whが空欄 | current_direction未確認、欠測、品質フラグ。符号を実機で確認。架空の数値で補完しない |
| 実測値が突然空欄 | 切断・停止・stale・画面とサーバーの無応答。最終BMS時刻とイベントを確認 |
| 航続距離が空欄 | 学習対象の終了走行が不足。30秒以上、0.05km以上、計測率90%以上、放電消費が正の走行を保存。部分GPSの距離は学習対象外 |
| Wh/kmが高すぎる | 手動距離誤入力、部分GPS距離、電流符号、充電を含むセッションを確認 |
| MOS温度が未対応 | NTCの設置場所が標準応答で不明。推測のラベル付けはしない |
| GPSが取得できない | gps_enabled=true、OS/ブラウザー位置許可、走行開始、位置プロバイダーを確認。手動距離は常に利用可能 |
| GPSの最高速度・標高が空欄 | 有効な位置差/標高の測定が不足。手動距離から最高速度を作らない |
| SQLiteエラー/容量不足 | ディスク空き、アクセス権、ウイルス対策のロックを確認。既存DBを削除せずバックアップ保全 |
| バックアップ失敗 | backups書き込み権限・空き容量、Windowsファイルロック。診断のmaintenance.errorを確認 |
| POSTが403 | ページ再読込で新しいローカルトークンを取得。CLIは/api/sessionのtokenをX-GTBMS-Tokenへ |
| localhostへつながらない | Start.ps1の起動、ポート8765競合、healthを確認。外部アドレス0.0.0.0へ変更しない |
| Watchdogが終了 | 別のサーバー/Watchdogが同ポートで起動中の可能性。既存起動を確認し重複を解消 |
| 自動起動しない | タスク実行ユーザー、Interactive、実行パス、サインイン状態、タスク履歴を確認 |
| スリープ後に欠測 | 想定動作。復帰後に再初期化。画面オフとスリープを区別して電源設定を確認 |
| 同期がoffline | HTTPS URL、認証環境変数、受信側ack契約を確認。アイテムはoutboxに保持されBMS監視は継続 |

## DB復旧

アプリと自動起動タスクを停止してください。現在のDBとWAL/SHMを別フォルダーへ保全し、終了した後のファイルだけを扱います。整合性確認済みのbackups/gtbms-*.sqlite3をdata/gtbms.sqlite3へコピーし、古いWAL/SHMを保全先へ移します。再起動前に `python -m gtbms.cli integrity` を実行します。復旧後に未送信データが再送される可能性があるため受信側UUID重複排除が必要です。

アドレス・位置・認証情報を含むconfigやGPS DBを公開issueへそのまま添付しないでください。アプリログは例外のクラス名を記録します。より詳しい通信解析は利用者の管理するローカルで行い、共有前に個人情報を確認します。

開発用pytestが既存TEMPのアクセス拒否になる場合は、未使用の作業フォルダー内パスを `--basetemp artifacts\pytest-new-run` に指定し、`-p no:cacheprovider` を付けます。Gitで別ユーザー所有の警告が出る場合は、このプロジェクトの作成元を確認したうえで `git -c safe.directory=C:/path/to/gt-bms-monitor status` のように正確なパスだけを指定できます。全パスの検査を無効にする設定は不要です。
