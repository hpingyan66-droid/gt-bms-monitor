# 法人管理・オープンソース提供・導入方式

更新日: 2026-10-12。依頼者から指定された提供・管理方針を記録する。役割分担とOSS提供、3種類の配布パッケージ、クイック導入・手動導入を採用する。第1段階の実装範囲は [配布仕様](PACKAGES.md)。法人の利用者認証・資格解除は次段階。

## 1. 管理主体と役割分担

| 項目 | 管理・判断する主体 | 開発者の担当 |
| --- | --- | --- |
| 採用する仕様・設計、変更の承認 | 導入先法人。依頼者は提供方針を定義 | 法人方針に沿った設計提案・実装 |
| ソース、ビルド、模擬・自動テスト、修正 | 法人が採用版・受入基準を管理 | 開発・ビルド・テスト、結果と未検証範囲の提示 |
| 実機への導入・利用開始・更新の採用 | 法人管理者 | セットアップ・検証・復旧手順を提供 |
| 利用者登録・資格確認・役割付与 | 法人管理者 | 機能と操作手順を実装 |
| 解除コード発行・失効・アクセス履歴 | 法人管理者 | 仕組みの設計・試験。常設の運用アクセスは持たない |
| 日々の利用、端末・無線・電源管理 | 法人と利用ユーザー | 障害の診断手順・修正を提供 |
| 実測データ、出力、バックアップ、保管・削除 | 法人と利用ユーザー | 分離と保護、運用機能の実装 |
| 操作の判断、実車運用、安全確認 | 法人と利用ユーザー | 測定値の品質・未確認事項・機能の制約を表示 |

この表は運用上の担当と判断権を定める。法的責任の一切が表や免責文だけで移転・消滅すると保証するものではない。利用条件・サポート条件・各法人の運用規程は、実際の提供形態に合わせて定める。

個人利用を行う現在の開発依頼者は、自分の端末の管理者としてフルアクセス版を維持する。法人配布時には開発者のアカウント・設定・データ・鍵を引き継がない。

## 2. 開発者と実運用のアクセスを分離

開発者向けフルアクセスパッケージは開発者本人の環境に提供する。現在の依頼者本人のフルアクセスは実測利用でも維持する。これだけで法人顧客の実運用環境・データへのアクセス権は生じない。ビルドに全導入先共通のマスターコードを含めない。

実運用の特別アクセスは、法人管理者が資格を確認して登録した担当者へ発行する。対象資格は第二種電気工事士、または1級・2級・3級・特殊のいずれかの自動車整備士。両方の保有は不要。資格条件の確認記録・利用者・対象導入先・許可範囲を結び付ける。

開発者が資格も持って実機受入を行う必要がある場合でも、開発者権限を流用しない。法人が個別に依頼・許可した対象、期間、操作範囲で資格者等として登録する。開発者へ実測DBや遠隔接続を自動送信しない。

コードの発行は法人管理者、コードの使用は本人認証済みの対象者。1回利用・期限付きは提案の段階。通常4モード、乗車時の制限、スマホ閲覧専用、BMS読み取り専用は別の制約として維持する。詳細は [専用解除案](ELEVATED_ACCESS_PROPOSAL.md)。

## 3. オープンソースとして提供

ソースコード、ビルド手順、依存版、テスト、設計資料、変更履歴、OSS通知を提供対象とする。現行プロジェクトのLICENSEはMIT。今回ライセンス文面や著作権表示を変更していない。採用する配布版では、任意・推移依存を含めた通知を揃える。

公開物から導入先固有設定、Bluetoothアドレス、閲覧キー、解除コード、認証DB、測定履歴、GPS、資格証情報、Wi-Fi設定、実ログを除外する。営業デモには明示した模擬データだけを同梱し、顧客の実測へ混ぜない。

法人は採用版と自社変更版を識別し、受入確認と運用を管理する。OSSのソースを保持するWindows管理者による改変を、アプリ内の役割機能で防ぐDRMとは説明しない。提供元への常時接続、開発者用の隠れた遠隔管理、常設の遠隔停止機能を導入の条件にしない。

## 4. 2種類の導入経路

### クイックインストールと今後の拡張

第1段階は版別ZIPのQuick-Install.cmdから専用venvと依存を準備する。公式Python 3.12以降は利用者が事前に用意する。Python同梱EXE/MSIではない。以下のうち法人管理者登録は次段階とし、初版は模擬起動・手動設定を案内する。

1. Windows/CPU/Pythonのアーキテクチャを確認する。x64/ARM64を区別し、未検証の組合せは明示。
2. アプリの専用環境を準備し、依存関係と配布版を検証する。Codex同梱Pythonを前提としない。
3. 後続段階で法人管理者を初回登録する。既定の共通パスワードや開発者の管理アカウントを作らない。
4. 模擬モードで画面・保存・診断を確認する。実BLE対象の登録と電流方向確認は法人側の受入手順へ進む。
5. 必要な場合にスマホ閲覧、自動起動、バックアップ先を案内する。Firewall・ホットスポット・ドライバー等を黙って変更しない。
6. 導入結果・版・検証結果・ログの場所を表示する。更新前バックアップと旧版への復旧方法を示す。

「ワンクリックで実機運用まで無条件に完了」とは扱わない。法人の確認が必要な設定は明示する。オンライン導入は依存取得に通信が必要だが、導入後の通常監視は既存のオフライン要件を維持する。完全オフライン導入が必要な場合は、依存を含む別パッケージの版・ライセンス・整合性を検証する。

### 手動セットアップ版（既存手順を拡張）

公開ソースを展開し、対応するPython、仮想環境、依存を導入して診断する手順を提供する。現状の `scripts/Setup.ps1` はPython 3.12以降の検出、既存.venv再利用、pip導入、設定例コピー、doctorまでを実装済み。法人管理者の初期登録と権限機能は未実装。

現在の手動セットアップ入口:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Setup.ps1
```

開発・検証用の `-WithTests` は一般利用者に必須としない。配布用SetupはCodex専用ランタイムの自動探索を外す。既存venvは維持する。クリーンなx64/ARM64環境での導入受入は残件。

## 5. 配布前の受入と次の実装

- 資格者の条件と法人の管理責任分担は今回の指定を採用する。4モードの細かな権限とコード期限は従来案から引き続き判断待ち。
- 第1段階は法人用・個人用・フルアクセス用を作成する。法人用と個人用は監視・走行記録・履歴出力を許可し、管理操作を制限する。次段階で法人管理者登録・役割付与・専用解除を整える。
- クリーンなWindows x64/ARM64で導入・再導入・更新・失敗復旧を試験する。既存の正常版・設定・DBを上書き破棄しない。
- 配布版のソース/ビルド対応、依存・通知、模擬/実機混入、機密情報非同梱、認証の初期化、開発者の実運用アクセス拒否を検証する。
- Build-Release.pyは版とビルド識別子を付けた新規ZIPを作り、既存出力への上書きを拒否する。
- GitHub公開先は [gt-bms-monitor](https://github.com/hpingyan66-droid/gt-bms-monitor) とする。署名付きインストーラーと自動更新は未実装。第1段階はソースZIPと操作制限を実装し、署名付きバイナリや自動更新は後続段階。
