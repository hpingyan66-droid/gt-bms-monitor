# 開発者・資格者の専用解除とフルアクセス案

2026-10-12 / 専用解除コード・本人認証は提案段階で未実装。

フルアクセスの配布区分と依頼者本人の現環境維持は採用済み。第1段階では [3種類のパッケージ](PACKAGES.md) を別々に作成する。本書の専用解除・資格照合・期限付きセッションは、パッケージの版名とは別の後続機能。

依頼: 開発者と資格者向けに専用解除コードを使うフルアクセスモードを追加する検討。資格者は管理する本人・法人が資格を確認した担当者であり、AIが資格を認定するものではない。追加回答で、第二種電気工事士、または1級・2級・3級・特殊のいずれかの自動車整備士を対象とすることが確定した。両方は不要。この確定は資格者の登録条件であり、コード方式・期限・権限表全体の実装承認を意味しない。

登録条件は `(第二種電気工事士 OR 自動車整備士{1級,2級,3級,特殊}) AND 本人・法人管理者による確認済み`。自動車整備士は各区分の種類を記録するが、指定された4区分内で特定の種類を勝手に除外しない。第一種電気工事士だけを持つ人や、2級電気工事施工管理技士など別資格は、今回の指定から自動追加しない。対象を広げる場合は提供元が明示的に決める。

資格の正式名称・区分の参考: [経済産業省・電気工事資格の案内](https://www.meti.go.jp/information/license/c_text24.html)、[国土交通省・自動車整備士技能検定制度](https://wwwtb.mlit.go.jp/chubu/seibi/seido.html)。これらは名称確認の資料で、アプリの登録条件は依頼者が決めた運用方針。資格保有だけでBMSの設定変更権限を生じさせない。

## 1. モードと対象者

通常のサービスマン／販売店／監視／乗車の4モードを残し、認証済みの対象者にだけフルアクセスへの解除操作を提供する案。フルアクセスの中で開発者と資格者を区別し、操作記録にも残す。

| 対象 | 事前登録の条件 | 解除後の用途 |
| --- | --- | --- |
| 開発者 | 開発・ビルド・テストを担当。現依頼者は自分の環境でフルアクセスを維持 | 担当する環境の全アプリ機能。顧客端末への常設アクセスは付与しない |
| 資格者 | 第二種電気工事士、または1級・2級・3級・特殊自動車整備士のいずれかを本人・法人管理者が確認して登録し、導入先の所有者も許可 | 全計測表示、詳細診断、アプリ設定、走行分析、点検資料 |

両者とも、導入先の所有者が委任した当該アプリ機能を広く使う。資格保有や開発者登録そのものから、すべての顧客端末・全顧客データへのアクセス権は発生しない。

資格登録には担当者ID、資格の種類、確認者、確認日、資格の有効期限（該当する場合）と登録の有効期限を保持する案。資格証画像や証明番号全体を通常ログへ保存しない。証明の保管が必要かは別途決める。

## 2. フルアクセスの範囲

| 機能 | フルアクセスの候補 |
| --- | --- |
| 現在値、セル、保護状態、通信・欠測診断 | 当該端末・車両の全項目 |
| 平均電力、観測ピーク、電費、走行履歴 | 所有者が許可したデータ範囲 |
| 収集開始停止、取得周期、アプリ通信設定 | 停車中、設定の検証・保存・操作記録を伴う |
| ネットワーク3モードと閲覧設定 | Surfaceから、既存のWindows権限・UAC条件の範囲内 |
| 出力・バックアップ・復旧・距離訂正 | 実装・承認された機能に限る。出力範囲・データ保護・復旧前バックアップは維持 |
| 独立模擬デモ、開発用の診断表示 | 実測との分離、秘密の除外、模擬ラベルを維持 |
| コード発行、役割の付与・資格登録の変更 | 所有者の管理権限が別途必要。解除された担当者への自動付与はしない |
| BMS保護解除、MOS制御、バランス設定、FW書換え | 全員対象外。読み取り専用を維持 |
| 任意のBLEコマンド、任意のシェル、DB直接編集 | フルアクセスのために新しく公開しない |

フルアクセスはアプリ内の機能範囲であり、Windows管理者権限を得るものではない。資格があることを理由に警告、計測値の品質、欠測除外、対象車両の制限を取り払わない。

## 3. 専用解除コードの初版案

後続段階は **導入先の本人・法人管理者がSurface上で発行する、一回利用・期限付きのコード** を推奨する。全顧客で共通するマスターコードや、ソースコードに固定した解除番号を使わない。

1. 所有者が本人認証し、登録済み対象者と役割、対象導入先・車両、許可範囲、期限を指定する。所有者が保有しない権限は発行できない。
2. 安全な乱数から十分な長さのコードを生成し、発行直後だけ所有者へ表示する。短い共有PINは使わない。具体的な文字数と入力形式は実装時に検証する。
3. 対象者は自分のアカウントで認証後、Surfaceへコードを入力する。コードだけでログインや資格登録を完了させない。対象者・導入先・役割に加え、発行後に縮小・失効していない現在の許可をサーバーが再検査する。
4. コードの一致検査と未使用確認、消費、昇格付与を原子的に処理する。二重クリック・同時要求でも再利用できないようにする。
5. コード自体の入力期限と、解除後セッションの有効期限を分ける。仮の候補は発行後10分以内の利用、解除後30分。これらの長さは承認待ちで、設定として確認する。
6. 期限切れ、手動ロック、ログアウト、資格・役割・コードの失効で解除を終了する。認証管理プロセスの再起動とスリープ復帰では未使用コードと昇格状態の両方を失効する初版案とする。通常閲覧へ戻し、BMS収集や走行記録を暗黙に停止しない。

昇格は本人の認証済みセッションだけに結び付ける。アプリ全体で共有する「フルアクセス中」フラグにせず、他の利用者・スマホ・別セッションへ権限を広げない。

コードは照合用の一方向ハッシュ等だけを保存し、入力値を通常ログ・URL・Git・作業報告・クラウド成果物へ出さない。閲覧キー、BMS接続パスワード、解除コードは別の認証情報として扱う。資格の有効期限がある場合、昇格期限はそれを超えない。

誤入力には遅延と試行回数制限を設け、再起動だけで無制限に再試行できないようにする。正規の所有者まで永久に締め出す固定ロックを避け、所有者認証による失効・再発行経路を設計する。回復用の共通裏口は作らない。

## 4. オフラインと失効

- 発行・照合・操作はSurface内で完結し、インターネット接続を必須にしない。コードをこのチャットで生成・受け渡ししない。
- 稼働中の期限は単調時計も使い、PC時計の後戻り等の不整合時には昇格を終了する。アプリ再起動後に解除状態を引き継がない。
- 当該Surfaceでの失効は既存タブ・WebSocket・進行中の権限操作へ反映する。完了済みの出力や持ち出したファイルを後から回収できるとは扱わない。
- 完全オフラインの他端末へ、遠隔で即時に資格失効を伝えることはできない。所有者が管理する端末内の登録・期限が有効性判断の根拠となる。将来中央発行を採用する場合は、この限界を含めて別設計とする。
- 同じWindowsユーザーや管理者によるアプリファイル改変、時計・認証DB・古いバックアップの悪意ある復元まで防ぐ耐改ざん保証は初版の対象外。通常のバックアップ復旧では既存コード・昇格セッションを無効化する手順を設ける。

## 5. スマホと乗車状態

初版の解除はSurface側だけ。現在のスマホ閲覧キーでフルアクセスへ上がれないようにし、LAN閲覧APIへコード発行・入力・管理操作を追加しない。

乗車状態では解除操作を提供せず、停車後にSurfaceで乗車モードを明示解除してから本人認証する。GPSや速度がないことは停車の証拠にしない。アプリの操作制限であり、自動の停車安全確認ではない。

## 6. 実装差分と受入

既存の4モード案に、登録された対象者、資格確認情報、コード発行/照合/消費/失効、時間制限付きの昇格セッション、監査記録を追加する。main・networkの両サーバーで権限の一貫性を保ち、GET履歴/export、変更API、WebSocketへ適用する。認証の保存方式やプロセス間伝達の詳細は実装前に検証する。

試験項目は、対象者・役割・導入先違い、未確認/期限切れ資格、コード期限切れ、再利用、同時利用、誤入力制限、時計変更、ログアウト/失効/再起動、複数タブ、バックアップ復旧、秘密ログ非出力、スマホ閲覧キー流用拒否、BMS読み取り要求のみを維持すること。

この専用解除方式は未実装で、個人の資格証確認・コード発行は実施していない。登録条件の指定は受領済み。第1段階の配布版制限は別仕様として実装する。

## 7. 決定が必要な項目

- 初版を「所有者によるローカル発行＋対象者認証＋一回利用＋期限付き」にするか。
- コード入力期限と解除セッション期限（10分/30分は候補）。
- 個人の資格確認方法、資格失効時の登録更新手順。対象資格と本人・法人管理者による確認という条件は決定済み。
- 所有者専用の権限管理とBMS読み取り専用を残す、アプリ内フルアクセスの範囲。

代替は導入先別の固定解除パスワードだが、共有・再利用・担当者退任時の管理が増える。中央で署名した解除許可を発行する案は、発行鍵の管理とオフライン失効の設計が増えるため初版から分ける。どちらも共通の固定裏口は採用しない。
